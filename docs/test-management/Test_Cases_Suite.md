# Набор тестовых сценариев (Test Cases Suite) — СОУИ

**Объект тестирования:** Система обработки учебной информации (СОУИ)[cite: 1, 2]  
**Тестовые уровни:** Database Testing (SQL), REST API Testing, GUI/E2E Flows, Security & Traffic Inspection[cite: 2]  
**Стандарты:** ISO/IEC/IEEE 29119, RESTful API Conventions[cite: 1]

## 1. Модуль «Справочники» (Dictionaries & Master Data)

### CRS-01: Успешное создание специальности
* **Приоритет:** High | **Тип:** Позитивный / Functional
* **Предусловия:** База данных доступна[cite: 2].
* **Шаги:**
  1. Открыть форму добавления специальности[cite: 2].
  2. Ввести название: `«Прикладная информатика»`[cite: 2].
  3. Ввести код: `«ПИ»`[cite: 2].
  4. Подтвердить сохранение[cite: 2].
* **Ожидаемый результат:** Запись успешно создана в таблице `specialty`, статус HTTP 201 / отображение в списке[cite: 2].

### CRS-04: Валидация формата названия специальности (запрет латиницы)
* **Приоритет:** Medium | **Тип:** Негативный / Input Validation (Regex)
* **Шаги:**
  1. Ввести название: `«Informatics»` (латиница)[cite: 2].
  2. Ввести корректный код: `«ИН»`[cite: 2].
  3. Отправить форму[cite: 2].
* **Ожидаемый результат:** Ошибка валидации формата. Ввод латиницы заблокирован (разрешены только русские буквы)[cite: 2].

### CRS-06: Проверка уникальности кода специальности
* **Приоритет:** High | **Тип:** Негативный / Data Integrity
* **Предусловия:** В БД существует специальность с кодом `«ПИ»`[cite: 2].
* **Шаги:**
  1. Попытаться создать новую специальность с кодом `«ПИ»`[cite: 2].
* **Ожидаемый результат:** Ошибка уникальности `Unique constraint violation` (код 409 / 422), дубликат не создан[cite: 2].

### GRP-10: Сортировка справочника групп по названию
* **Приоритет:** Low | **Тип:** Functional / UI
* **Предусловия:** В системе есть группы `«ВТ-21»`, `«АП-21»`, `«БИ-21»`[cite: 2].
* **Шаги:**
  1. Открыть справочник групп[cite: 2].
  2. Применить сортировку по названию[cite: 2].
* **Ожидаемый результат:** Записи упорядочены по алфавиту: `«АП-21»`, `«БИ-21»`, `«ВТ-21»`[cite: 2].

### STD-06: Валидация ФИО студента (только кириллица)
* **Приоритет:** Medium | **Тип:** Негативный / Regex Validation
* **Шаги:**
  1. Заполнить поле «Фамилия» значением `«Smith»`[cite: 2].
  2. Заполнить остальные обязательные поля корректными данными[cite: 2].
  3. Отправить запрос на создание[cite: 2].
* **Ожидаемый результат:** Система блокирует отправку / возвращает `422 Unprocessable Entity`[cite: 2].

### STD-10: Проверка уникальности номера студенческого билета
* **Приоритет:** High | **Тип:** Негативный / Integrity Constraint
* **Предусловия:** Зарегистрирован студент с номером билета `101001`[cite: 2].
* **Шаги:**
  1. Попытаться зарегистрировать нового студента с номером билета `101001`[cite: 2].
* **Ожидаемый результат:** Отказ в сохранении, ошибка нарушения уникальности `UNIQUE(student_card_number)`[cite: 2].

### SUB-07: Граничные значения: проверка количества часов предмета (<= 0)
* **Приоритет:** High | **Тип:** Негативный / Boundary Value Analysis (BVA)
* **Шаги:**
  1. Создать предмет с `hours_count = 0`[cite: 2].
  2. Создать предмет с `hours_count = -10`[cite: 2].
* **Ожидаемый результат:** Ошибка валидации `CHECK (hours_count > 0)`[cite: 2]. Сохранение запрещено[cite: 2].

## 2. Модуль «Журнал успеваемости» (Journal Lifecycle)

### JRN-01: Выдача варианта задания студенту (начальное состояние)
* **Приоритет:** Critical | **Тип:** Позитивный / State Transition
* **Предусловия:** В БД созданы преподаватель, студент, контрольная точка и задание[cite: 2].
* **Шаги:**
  1. Создать запись журнала, выбрав преподавателя, студента, контрольную точку и задание[cite: 2].
  2. Поля «Оценка» и «Дата сдачи» оставить незаполненными (`null`)[cite: 2].
  3. Сохранить запись[cite: 2].
* **Ожидаемый результат:** Запись создана со статусом `null` для оценки и даты[cite: 2].

### JRN-02: Фиксация сдачи работы и выставление оценки
* **Приоритет:** Critical | **Тип:** Позитивный / State Transition
* **Предусловия:** Существует запись журнала без оценки (JRN-01)[cite: 2].
* **Шаги:**
  1. Открыть существующую запись на редактирование[cite: 2].
  2. Указать оценку `45` и дату сдачи = текущая дата[cite: 2].
  3. Сохранить изменения[cite: 2].
* **Ожидаемый результат:** Поля `grade` и `submission_date` обновлены, данные сохранены в БД[cite: 2].

### JRN-10: Граничные значения шкалы оценивания (BVA 0–60)
* **Приоритет:** Critical | **Тип:** Граничные значения (BVA)
* **Шаги и тестовые данные:**
  1. Выставить оценку `0` (Нижняя граница) $\rightarrow$ Успешно сохранено[cite: 2].
  2. Выставить оценку `60` (Верхняя граница) $\rightarrow$ Успешно сохранено[cite: 2].
  3. Выставить оценку `61` (Верхняя граница +1) $\rightarrow$ Ошибка валидации[cite: 2].
  4. Выставить оценку `-1` (Нижняя граница -1) $\rightarrow$ Ошибка валидации[cite: 2].
  5. Выставить оценку `999` $\rightarrow$ Ошибка валидации[cite: 2].
* **Ожидаемый результат:** Значения в диапазоне `[0; 60]` принимаются; любые значения вне диапазона отклоняются СУБД и API[cite: 2].

## 3. Модуль «Режим преподавателя (Работа)» (Filtered Views)

### WRK-01: Контекстная фильтрация записей по преподавателю и предмету
* **Приоритет:** High | **Тип:** Functional / Filtering Logic
* **Предусловия:** В журнале есть записи преподавателя Иванова (Математика) и Петрова (Физика)[cite: 2].
* **Шаги:**
  1. В режиме «Работа» выбрать: Преподаватель = Иванов, Предмет = Математика[cite: 2].
  2. Запросить выборку журнала[cite: 2].
* **Ожидаемый результат:** В ответе возвращаются только записи Иванова по Математике[cite: 2]. Записи других преподавателей/предметов исключены[cite: 2].

### WRK-03: Добавление записи с автоматической фиксацией контекста
* **Приоритет:** High | **Тип:** Functional / Workflow
* **Предусловия:** Открыт журнал в контексте Иванов / Математика[cite: 2].
* **Шаги:**
  1. Выполнить действие «Добавить запись»[cite: 2].
  2. Выбрать студента, КТ и задание[cite: 2].
* **Ожидаемый результат:** Поле «Преподаватель» предзаполнено значением `Иванов`, список заданий ограничен предметом `Математика`[cite: 2].

## 4. Модуль «Отчёты и Сводная ведомость» (Reporting & Aggregations)

### RPT-06: Формирование сводной ведомости (без фильтров)
* **Приоритет:** High | **Тип:** Aggregation / Business Logic
* **Предусловия:** В журнале присутствуют записи разных групп и предметов с оценками[cite: 2].
* **Шаги:**
  1. Запросить генерацию сводной ведомости без указания параметров[cite: 2].
* **Ожидаемый результат:** Сформирован отчет со структурой: `Группа`, `Предмет`, `Средний балл`, `Количество контрольных точек`[cite: 2].

### RPT-09: Фильтрация ведомости по диапазону дат
* **Приоритет:** Medium | **Тип:** Data Filtering
* **Предусловия:** В БД имеются сдачи от `2026-01-15` и `2026-02-20`[cite: 2].
* **Шаги:**
  1. Задать фильтр периода с `2026-01-01` по `2026-01-31`[cite: 2].
  2. Сформировать отчет[cite: 2].
* **Ожидаемый результат:** В отчет включены только данные за январь 2026 года[cite: 2].

### RPT-13: Проверка корректности математических агрегаций (AVG/COUNT)
* **Приоритет:** Critical | **Тип:** Calculation Accuracy
* **Предусловия:** Студент группы `ИС-21` имеет оценки `40` и `60` по Математике[cite: 2].
* **Шаги:**
  1. Сформировать ведомость для группы `ИС-21` по Математике[cite: 2].
* **Ожидаемый результат:** Расчетный средний балл равен строго `50.0`, количество точек = `2`[cite: 2].

## 5. Ссылочная целостность и Database Constraints (SQL Level)

### TC-INT-01: Запрет каскадного удаления специальности при наличии групп
* **Приоритет:** Critical | **Тип:** Database / Foreign Key Constraint
* **Предусловия:** Специальность `specialty_id = 1` привязана к группе `group_id = 1`[cite: 2].
* **Шаги:**
  1. Выполнить SQL: `DELETE FROM specialty WHERE specialty_id = 1;`[cite: 2]
* **Ожидаемый результат:** Ошибка `foreign_key_violation` (`ON DELETE RESTRICT`)[cite: 2]. Удаление отклонено СУБД[cite: 2].

### TC-INT-02: Запрет удаления студента при наличии записей в журнале
* **Приоритет:** Critical | **Тип:** Database / Foreign Key Constraint
* **Предусловия:** Студент `student_id = 1` имеет запись в таблице `journal`[cite: 2].
* **Шаги:**
  1. Выполнить SQL: `DELETE FROM student WHERE student_id = 1;`[cite: 2]
* **Ожидаемый результат:** Ошибка нарушения внешнего ключа[cite: 2]. Данные студента сохранены[cite: 2].

## 6. Тестирование сетевого трафика и устойчивости API (Charles / Postman)

### TC-SEC-01: Перехват и подмена тела запроса (Breakpoints)
* **Инструмент:** Charles Proxy / Fiddler
* **Шаги:**
  1. Перехватить запрос `POST /api/subjects`[cite: 2].
  2. Подменить JSON на: `{"name": "Physics", "hours_count": -40, "semesters_count": 1}`[cite: 2].
  3. Отправить измененный запрос на сервер.
* **Ожидаемый результат:** Сервер не падает с `500 Internal Server Error`, а возвращает клиентскую ошибку `422 Unprocessable Entity`[cite: 2].

### TC-SEC-02: Обработка некорректного диапазона дат (start_date > end_date)
* **Шаги:**
  1. Отправить запрос `GET /api/reports/summary?start_date=2026-02-01&end_date=2026-01-01`[cite: 2].
* **Ожидаемый результат:** Статус `400 Bad Request` с информативным сообщением об ошибке интервала либо пустой список данных без падения сервиса.
